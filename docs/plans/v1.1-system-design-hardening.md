# v1.1 — System-design hardening (ACCEPTED)

> Amends [v1.0](v1.0-architecture.md); everything v1.1 does not change stands. Change history: [CHANGELOG](CHANGELOG.md).
> Accepted 2026-11-18, before P3, at the owner's request: confirm every system-design concern is covered, with proper rate limiting and self-healing.

## 1. Why

P2 closed with the request path built and tested. Measured against a full system-design checklist, v1.0 was strong on per-call resilience but had gaps:

| Gap in v1.0 | Consequence |
|---|---|
| One rate-limit bucket per client, failing open | Blind to tool cost and identity; unlimited during a DynamoDB outage |
| No self-healing catalogue | Recovery paths existed piecemeal (breakers, canary rollback, DLQ) with no detection, verification or owner for the rest |
| No RPO/RTO, retention or capacity figures | DR, purges and connection budgets were implicit |
| Gateway never retried writes | A response lost after commit pushed the agent to retry with a new key |
| `POST /v1/audit` not idempotent | A retried audit write recorded a call twice |
| `ops.processed_events` promised for P2, not built | Consumers could not dedupe |

## 2. Changes to v1.0

| v1.0 section | Change | Designed in |
|---|---|---|
| §5 Rate limiting ("DynamoDB token bucket, 60 req/min, burst 20") | Eight layers: API Gateway throttling, optional WAF, per-principal and per-client buckets weighted by tool cost, outbound quotas, concurrency ceilings, connection budget; fail soft | [Resilience §6](../architecture/lld/resilience.md#6-rate-limiting-in-layers), [ADR 0015](../adr/0015-layered-rate-limits-weighted-and-fail-soft.md) |
| §5 Retry ("idempotent calls only") | Writes are retried by the gateway with their original key (2 attempts) | [System design §8](../architecture/system-design.md#8-idempotency-end-to-end) |
| §5 (new row) Self-healing | Detect → contain → recover → verify for every expected failure, automatic where safe | [Resilience §10](../architecture/lld/resilience.md#10-self-healing) |
| §6 SLOs (new rows) | RPO ≤ 5 min, RTO ≈ 1 h | [System design §6](../architecture/system-design.md#6-backup-and-disaster-recovery) |
| (new) | Consistency model, caching rules, data lifecycle, capacity estimates, API evolution | [System design](../architecture/system-design.md) |

## 3. Phase scope

| Phase | Adds | Exit criterion changes |
|---|---|---|
| **Before P3** | `ops.processed_events`; idempotent `POST /v1/audit` (`audit_id` from the gateway); `Idempotent-Replayed` header | none: it completes P2 |
| **P3** | Rate-limit layers 3–5 with headers and fail-soft fallback; same-key write retries; JWKS refetch on unknown `kid`; load shedding | Tool matrix also covers weights, both buckets, `429` headers, fail-soft and write retry after a lost response |
| **P4** | Visibility-timeout backoff in consumers; consumer dedupe; outbound limiter toward the screening vendor; a test per automatic self-healing row | "Breaker lifecycle demonstrated" widens to "every automatic row of resilience §10 demonstrated" |
| **P5** | OpenAI client-side RPM/TPM limiter and daily spend cap, degrading to full-text search | Degradation asserted in the RAG eval run |
| **P6** | API Gateway throttling; WAF if the plan allows; reserved and event-source concurrency; NAT automatic recovery; RDS backups, PITR and storage autoscaling; scheduled partition, purge and reconcile jobs; synthetic probe; secret refresh on auth failure; a restore drill | Restore drill timings recorded; synthetic probe green for 24 h |
